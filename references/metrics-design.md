# 指标体系设计

> 一个组织的行为，最终由它考核的指标决定。**指标设计是在设计激励**，不是在设计报表。
> 设计错了，团队会诚实地、勤奋地把公司带往错误方向。

## 一、好指标的六个标准

| 标准 | 含义 | 反例 |
|------|------|------|
| **可行动** | 指标变化能指向具体动作 | "总用户数"——涨了跌了都不知道该做什么 |
| **可归因** | 能定位到是谁、哪个环节导致的 | 全站 GMV，波动来源无法拆解 |
| **敏感** | 产品改动能在合理时间内反映出来 | 年留存率，改一次要等一年才知道 |
| **抗操纵** | 不能通过损害用户价值来刷高 | "页面停留时长"——把加载做慢就能涨 |
| **口径唯一** | 所有人算出同一个数 | "活跃用户"每个部门定义不同 |
| **有对照** | 有基准、目标或同比可比 | 孤零零一个 "3.2%" 无法判断好坏 |

**抗操纵性最容易被忽视**。设计任何考核指标时，主动问："如果我只想让这个数字变好看，
不惜损害用户，我会怎么做？"如果答案很容易想到且难以察觉，这个指标不能用于考核。

## 二、指标分层

```
北极星指标（1 个）
  └─ 一级指标（3-5 个）      主要驱动因素
       └─ 二级指标           一级指标的乘法/加法拆解
            └─ 过程指标      团队日常可直接影响的
                 └─ 护栏指标 不能变差的底线
```

**北极星指标**必须同时满足：反映用户获得的价值、与长期收入正相关、团队可影响。

| 业务 | 北极星 | 为什么不是别的 |
|------|--------|--------------|
| 内容平台 | 有效阅读时长 | 不是 PV——PV 可以靠标题党刷 |
| 电商 | 复购用户数 | 不是 GMV——GMV 可以靠补贴买 |
| SaaS | 周活跃团队数 | 不是注册数——注册不等于在用 |
| 工具 | 完成核心任务次数 | 不是打开次数——打开了没用上等于失败 |

**护栏指标**是北极星的对偶：防止为了拉北极星而破坏其他东西。
常见护栏：崩溃率、页面延迟、退款率、投诉率、取关率、客服工单量。

## 三、乘法拆解：让指标可归因

把顶层指标拆成互相独立的乘数，每个乘数对应一个可负责的团队/环节。

```
GMV = 访问用户数 × 转化率 × 客单价 × 复购频次
                    ↑           ↑          ↑
                  产品体验    商品定价   运营留存
```

```
DAU = 新增 + 回流 + 留存
    留存 = 昨日活跃 × 次日留存率
```

拆解的质量标准：
- **MECE**：不重不漏。乘完/加完必须等于顶层指标，能对上账
- **每一项有明确 owner**：没人负责的项等于没拆
- **每一项可独立改善**：如果改 A 必然导致 B 变差，说明拆解维度选错了

拆解的用法：指标异动时**逐层下钻定位**。GMV 跌了 8%，
先看四个乘数各变了多少，找到主要贡献项，再在那一项里继续拆维度（渠道、品类、地区）。

## 四、比率类指标的三个陷阱

### 分母漂移
转化率下降，常常是分母口径变了（比如把新渠道的低质流量算进来），分子并没有变差。

**规则**：任何比率必须同时展示分子和分母的绝对值走势。只看比率必然误判。

### 辛普森悖论
各细分都在涨，整体在跌——因为结构变了。见 `exploratory-analysis.md`。

**规则**：整体比率的变化要做**结构分解**：
```
Δ整体率 = Σ(各组率的变化 × 原结构权重)  +  Σ(各组结构变化 × 原组率)
           ────────── 效率变化 ──────────    ────────── 结构变化 ──────────
```
分清是"每个环节变差了"还是"用户结构变了"，两者的应对完全不同。

### 小分母噪声
某个细分只有 30 个样本，转化率从 10% 跳到 20% 只是多了 3 个人。

**规则**：给所有比率设最小分母阈值，低于阈值的显示为"样本不足"而不是显示数字。
或者用置信区间下界排序，而不是用点估计排序。

## 五、口径管理：同一个词只能有一个意思

指标口径失控是数据团队最大的信任损耗来源——业务方发现两个报表数字不一样，
从此不再相信任何数字。

**指标定义必须包含七要素**：

```yaml
name: 日活跃用户数 (DAU)
definition: 当日有至少一次核心行为的去重用户数
entity: user_id（登录用户）；未登录用户按 device_id 计，不与登录用户合并
core_action: 浏览详情页 / 下单 / 评论（不含仅打开 App）
time_window: 自然日，UTC+8，00:00:00 - 23:59:59
filters: 排除内部测试账号、已识别爬虫、风控标记的刷量账号
source: dwd.user_events（不要直接查 ods）
owner: 数据平台组 @someone
updated: 2026-08-06，历史口径变更见 changelog
```

配套机制：
- **单一定义源**：口径写在一处（指标平台 / dbt metrics / 文档），所有报表引用它，
  不允许各自在 SQL 里重新写一遍
- **变更需评审并留痕**：口径变更必须记录生效日期，历史数据是否重算要明确
- **图上标注口径版本**：跨越口径变更日的趋势图，必须标出变更点，否则会读出虚假的跳变

## 六、指标的时间属性

同一个业务问题，选错时间窗会得到相反结论。

| 时间概念 | 说明 | 易错点 |
|---------|------|--------|
| 事件时间 vs 到达时间 | 事件发生 vs 数据入库 | 按到达时间统计，迟到数据会算到错误的日期 |
| 滚动窗口 vs 自然周期 | 近 7 天 vs 本自然周 | 自然周期在周初样本少，波动大 |
| 同期群 vs 快照 | 按加入时间分组追踪 vs 当前状态 | 快照口径下"留存率"会随新增量变化，不反映真实留存 |
| 观察期成熟度 | 7 日留存需要等 7 天 | 最新 cohort 数据未成熟，不能与历史比较 |

**跨时区业务**：统一 UTC 存储，报表按业务主时区聚合，并在图上标注时区。
"昨天"这个词在跨境业务里必须消歧。

## 七、指标腐化：需要定期体检

指标不是一次设计就永久有效：

- **埋点漂移**：客户端改版后某个埋点没上报，指标悄悄少了一块
- **口径遗忘**：设计者离职，后来者按字面意思理解，逐渐用错
- **目标固化**（古德哈特定律）：当指标成为目标，它就不再是好指标
- **业务变化**：产品形态变了，原来的核心行为不再是核心

**季度体检清单**：
- [ ] 每个指标是否仍有人真正在用来做决策？没有就下线
- [ ] 埋点覆盖率与上报成功率是否稳定？
- [ ] 是否出现了明显的指标操纵行为？
- [ ] 北极星指标与营收/留存的相关性是否仍然成立？（用历史数据验证）
- [ ] 口径文档是否与实际 SQL 一致？

## 八、指标异动归因的标准流程

指标突然波动时，按顺序排除，**不要跳过前两步直接找业务原因**：

```
1. 数据问题？    埋点故障、任务失败、数据未回齐、口径变更
                 ← 至少 40% 的"异动"止步于此
2. 统计噪声？    波动是否超出历史同期的正常范围（用 P5-P95 判断）
                 ← 周末效应、节假日、月末结算
3. 外部因素？    大促、竞品动作、政策、天气、热点事件
4. 内部变更？    发版、配置调整、运营活动、价格变动
                 ← 对齐变更日志，看时间点是否吻合
5. 结构变化？    做结构分解，区分效率变化与结构变化
6. 真实趋势？    以上都排除后，才是业务本身的变化
```

每一步都要有证据，不能靠"应该是……吧"。归因结论要能被复现：
"7 月 15 日 GMV 环比 -12%，其中 -9pp 来自 iOS 渠道转化率下跌，
与当日 14:30 上线的支付 SDK 版本时间吻合，回滚后恢复。"
