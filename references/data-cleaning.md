# 数据清洗与质量保障

> 清洗不是"把数据弄干净"，是**在信息损失最小的前提下，让数据符合分析假设**。
> 每一次清洗都是一次判断，判断就必须有依据、可复现、可回溯。

## 一、三条铁律

1. **永不原地修改源数据**。清洗输出到新文件/新表，保留原始层。
   分层：`raw`（一字不改）→ `staging`（清洗后）→ `mart`（业务口径聚合）。
2. **清洗必须是代码，不能是手工**。Excel 里手动删了几行，下个月没人复现得出同样的数字。
3. **每一步都要留下计数**。"清洗前 1,204,331 行，去重后 1,198,022 行，剔除异常 1,504 行，
   最终 1,196,518 行"——没有这串数字的清洗流程不可信。

## 二、按顺序做，顺序错了会互相污染

正确顺序及原因：

```
1. 结构对齐   列名、列数、编码、分隔符      ← 结构不对，后面全错
2. 类型转换   字符串 → 数值/日期            ← 类型不对，去重和比较都不可靠
3. 去重       明确"重复"的定义              ← 必须在类型统一后做
4. 缺失处理   先判断机制，再决定填/删/标    ← 在去重后做，避免重复行影响缺失率
5. 异常处理   业务规则优先于统计规则        ← 需要正确的类型和分布做依据
6. 标准化     单位、大小写、枚举值映射      ← 最后做，避免被前面步骤覆盖
7. 一致性校验 跨字段、跨表的逻辑约束        ← 收尾体检
```

**典型错序事故**：先去重再转类型 → `"100"` 和 `100` 被当成两条不同记录，重复没去掉。

## 三、类型转换：最容易埋雷的一步

| 场景 | 陷阱 | 正确做法 |
|------|------|---------|
| 数字型 ID | 被读成数值后前导零丢失（`007` → `7`），大整数精度丢失 | 显式指定为字符串 |
| 金额 | 千分位逗号、货币符号、括号表示负数 `(100)` | 先清符号再转，负数表示要确认 |
| 百分比 | `85%` 转成 85 还是 0.85 口径不一 | 统一存小数，列名标注单位 |
| 日期 | `03/04/2026` 是 3 月 4 日还是 4 月 3 日 | 强制指定格式，禁止自动推断 |
| 时间戳 | 秒 / 毫秒 / 微秒混用；无时区 | 统一 UTC 存储，展示时再转本地时区 |
| 布尔 | `1/0`、`Y/N`、`true/TRUE/True`、`是/否` 混用 | 建映射表统一，未命中的值报错而非默认 False |

**时区是最贵的坑**：跨时区业务里"昨天的数据"取决于用谁的昨天。
约定：**存储一律 UTC，聚合时显式声明时区**，并在报告里标注。
夏令时切换日会出现 23 小时或 25 小时的一天，按小时聚合时必须留意。

## 四、去重：先定义"什么算重复"

去重前必须回答：**主键是什么？**

| 情况 | 判断 | 处理 |
|------|------|------|
| 整行完全相同 | 多半是导出/导入重复 | 直接去重 |
| 主键相同、其他字段不同 | 更新历史，或数据冲突 | 按时间戳保留最新；无时间戳则**报错而不是随便留一条** |
| 业务重复但主键不同 | 同一用户注册了两个账号 | 这是业务问题，不是数据问题，要单独建实体映射 |
| 明细表天然多行 | 一个订单多个商品 | **不是重复**，误去重会丢数据 |

> 危险信号：去重后行数减少超过 5%。这通常意味着主键定义错了，
> 或者你正在把明细当成汇总来去重。停下来核对。

## 五、缺失值：填充是最后选项，不是第一选项

处理决策树：

```
这个字段缺失代表什么？
├─ 代表"不适用"（如未婚者的配偶姓名）
│   → 保留缺失，不填充。填了就是造假
├─ 代表"未发生"（如未支付的支付时间）
│   → 保留缺失；若做数值计算，按业务语义补 0 并注明
├─ 代表"未采集"（埋点上线前的历史数据）
│   → 限定分析时间窗，从埋点上线日开始
└─ 代表"采集失败"（真正的数据丢失）
    ├─ 缺失率 < 5%  → 删除这些行，记录删除量
    ├─ 缺失率 5-30% → 填充 + 增加 is_missing 标记列
    └─ 缺失率 > 30% → 这一列基本不可用，除非缺失本身有信息
```

填充方法及代价：

| 方法 | 适用 | 代价 |
|------|------|------|
| 均值 | 近似正态的数值 | 压缩方差，长尾数据会严重偏移 |
| 中位数 | 长尾数值（默认首选） | 同样压缩方差，但更稳健 |
| 众数 | 类别型 | 放大主类别占比 |
| 前向填充 | 时间序列的状态量 | 会把陈旧值带到很后面，要限制最大填充跨度 |
| 分组统计量 | 有明显分组差异时 | 更准确，但组内样本少时不稳 |
| 模型预测 | 缺失有规律且列间相关强 | 引入模型误差，且会人为放大变量间相关性 |
| 单独一类 | 类别型（填 "未知"） | **通常最诚实**，保留了"不知道"这个信息 |

**核心原则**：填充的目的是让流程能跑，不是让数据变好看。
凡是填充过的字段，在下游统计显著性检验时都要打折看待——填充值人为降低了方差。

## 六、标准化：把同义不同形的值合并

- **文本**：去首尾空格、统一大小写、全角转半角、Unicode 归一化（NFKC）。
  中文场景还要注意繁简、异体字。
- **枚举值**：`北京市` / `北京` / `Beijing` / `BJ` 建映射表。
  **未命中映射的值必须报警，不能静默归入"其他"**——静默归类会让新出现的枚举值悄悄消失。
- **数值单位**：同一列不允许混单位。列名带上单位，如 `amount_cny`、`duration_ms`。
- **地址/电话/邮箱**：用正则规范化，同时保留原始值列以便回溯。

## 七、一致性校验：跨字段的逻辑约束

这一层最容易被跳过，却最能发现真问题：

- **时间顺序**：`created_at ≤ paid_at ≤ shipped_at ≤ completed_at`
- **数值关系**：`折后金额 ≤ 原价`、`已用额度 ≤ 总额度`、`子项之和 = 总计`
- **枚举依赖**：`status = 'refunded'` 时 `refund_amount` 不能为空
- **参照完整性**：明细表的 `user_id` 必须在用户表中存在（孤儿记录是数据链路断裂的信号）
- **总量守恒**：清洗前后关键指标的总和应当对得上，对不上要能解释差额

把这些写成断言，用 `scripts/data_quality_check.py` 配合
`assets/data-quality-rules.json` 每次跑，而不是靠人记得检查。

## 八、把清洗变成可持续的质量保障

一次性清洗解决不了持续流入的脏数据。要在管道里设三道闸：

| 位置 | 检查 | 失败动作 |
|------|------|---------|
| **入口**（raw 落库时） | schema 是否变化、行数是否在合理区间、必填字段是否为空 | 告警但不阻断，保留原始数据 |
| **中间**（staging 产出后） | 主键唯一、缺失率阈值、取值域、跨字段一致性 | **阻断下游**，避免脏数据扩散 |
| **出口**（mart 产出后） | 核心指标同比环比波动、与上游总量对账 | 阻断发布，人工确认 |

阈值设定原则：**基于历史分布，不要拍脑袋**。
比如"日订单量"的告警下限用过去 30 天同星期几的 P5，而不是固定值——
固定值在业务增长后会永远不触发，在大促时会疯狂误报。

## 九、清洗日志：让每个数字可追溯

每次清洗输出一份结构化日志，至少包含：

```json
{
  "input_rows": 1204331,
  "output_rows": 1196518,
  "steps": [
    {"step": "dedupe", "removed": 6309, "rule": "primary key (order_id)"},
    {"step": "drop_na", "removed": 1504, "rule": "user_id is null"},
    {"step": "outlier", "flagged": 82, "rule": "amount > P99.9, kept with flag"}
  ],
  "warnings": ["column `region` 出现 3 个未在映射表中的新值: 西藏/澳门/未知"]
}
```

有了这份日志，三个月后有人问"为什么这个月少了 8000 单"，你能在 30 秒内回答。
没有它，你只能重跑一遍并祈祷结果一样。
