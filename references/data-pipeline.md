# 数据管道工程

> 管道的价值不在"能把数据搬过去"，在于**在故障、重跑、迟到数据、schema 变更之后，
> 结果依然正确**。跑通一次很容易，长期正确很难。

## 一、ETL 还是 ELT

| | ETL（先转换后加载） | ELT（先加载后转换） |
|--|-------------------|-------------------|
| 转换发生在 | 独立计算层 | 数仓内部（SQL） |
| 适合 | 数据源杂、需要清洗才能落库、合规要求脱敏前置 | 数仓算力充足（云数仓）、口径易变 |
| 优势 | 落库数据已干净、存储省 | 保留原始数据、口径改了可重算、开发门槛低 |
| 代价 | 口径变更要重新抽取；原始数据丢失 | 数仓成本高；raw 层杂乱 |

**默认选 ELT**，只要存储便宜。理由：口径一定会变，而原始数据一旦没落盘就再也回不来了。
唯一的例外是含个人隐私字段——脱敏必须在落库前完成。

## 二、分层：raw / staging / mart

```
raw      源系统的忠实副本，一字不改，只加载入时间戳与批次号
  ↓      只做类型转换、重命名、去重、基础清洗
staging  干净的明细，一行一个业务事实，粒度明确
  ↓      按业务口径聚合、关联维度
mart     面向消费的宽表/指标表，直接给报表和分析用
```

三层各自的铁律：
- **raw 层永不修改、永不删除**。它是所有重算的唯一依据。
- **staging 层保证唯一性和类型正确**。下游可以信任它的主键。
- **mart 层承载业务口径**。口径变更只改这一层，不用重新抽数。

**跨层禁止跳跃引用**：报表不能直接查 raw。允许一次，就会有一百次，
最后没有人知道某个数字到底是从哪层算出来的。

## 三、幂等：管道设计的第一原则

**幂等 = 同样的输入跑一次和跑十次，结果完全相同。**

不幂等的管道意味着重跑会产生重复数据，而重跑是必然会发生的（故障、修 bug、补数据）。

实现方式，按推荐度排序：

| 方式 | 做法 | 适用 |
|------|------|------|
| **分区覆盖写** | 每次重跑先 `DELETE WHERE dt = '2026-08-06'` 再插入，或直接 `INSERT OVERWRITE PARTITION` | 按日/小时分区的批处理，**首选** |
| **MERGE / UPSERT** | 按主键更新或插入 | 缓慢变化维、需要更新历史行 |
| **全量替换** | 写入临时表，成功后原子切换 | 小表、维度表 |
| **去重键** | 写入后按业务主键去重 | 流式场景的兜底 |

**反模式**：`INSERT INTO ... SELECT` 无任何删除。第一次跑对，第二次跑数据翻倍。
这是数据事故最常见的单一原因。

## 四、增量处理的三种模式与各自的坑

### 按时间戳增量
```sql
WHERE updated_at > {last_watermark}
```
**坑**：
- 源系统时钟不同步 / 事务提交时间晚于 `updated_at` → 会漏数据
- 边界用 `>` 还是 `>=` 决定重复还是遗漏
- 源库无 `updated_at`，或有但不更新（很常见）

**防御**：水位线回退一个安全窗口（如回退 1 小时重叠抽取），配合幂等写入。
宁可重复抽取再去重，不能漏。

### 按自增 ID 增量
只适合 append-only 表。更新历史行不会被捕获，删除更不会。

### CDC（变更数据捕获）
读数据库 binlog/WAL，能捕获增删改。最完整但也最复杂：
需要处理 DDL 变更、乱序、重复投递、大事务。
除非有平台支持，小团队慎用。

## 五、迟到数据与回填

**迟到数据**：属于昨天的事件，今天才到。移动端离线上报、跨境网络、上游重试都会导致。

处理策略：
- **按事件时间分区，而非到达时间分区**。这是前提，否则数据会落错分区。
- **设定重算窗口**：每天不只算 T-1，而是重算 T-1 到 T-3。用幂等写入保证安全。
- **超出窗口的迟到数据**：单独走补数流程，并在指标表标注"该日数据已于 X 时刻修订"。

**回填（backfill）** 的注意事项：
1. **回填必须走和日常一样的代码路径**。写一个"专门用来回填的脚本"，
   它和日常逻辑的差异迟早会造成历史数据与新数据口径不一致。
2. **限制并发**。同时回填 90 天会打爆源库和数仓，按天串行或小批并发。
3. **回填要能中断续跑**。记录已完成的分区，重启后跳过。
4. **回填期间下游要能感知**。给分区打标记，或暂停下游调度，避免读到半完成状态。

## 六、调度与依赖

**依赖必须显式声明，不能靠时间猜。**

反模式：上游 2:00 跑，那我 3:00 跑，应该跑完了吧。
上游某天慢了 90 分钟，你就在读昨天的旧数据，而且**不会报错**——这是最危险的失败模式。

正确做法：
- 用 DAG 编排（Airflow / Dagster / Prefect 等），下游依赖上游任务的成功状态
- 跨系统依赖用**数据就绪信号**：上游写完后打一个 `_SUCCESS` 标记或写一条元数据记录，
  下游轮询这个信号而不是等时间
- **依赖检查失败要阻断，不要降级**。宁可没数据，不要有错数据

**重试策略**：
- 区分**可重试错误**（网络超时、限流、资源竞争）和**不可重试错误**（schema 不匹配、
  权限不足、代码 bug）。后者重试只是浪费时间并延迟告警。
- 指数退避 + 抖动，最多 3-5 次
- 重试的前提是幂等。不幂等的任务重试就是在制造脏数据

**SLA 与告警**：给关键管道设置"应当在几点前完成"，超时告警。
只监控"失败"是不够的——卡住不动的任务永远不会报失败。

## 七、Schema 演进

上游加字段、改类型、删字段是常态，管道必须能优雅应对。

| 变更 | 影响 | 处理 |
|------|------|------|
| 新增字段 | 通常安全 | raw 层自动接收；staging 层显式声明列，新字段需要人工纳入 |
| 字段改名 | **静默断裂**：老字段变 NULL | 契约校验 + 告警；保留映射兼容期 |
| 类型变更 | 解析失败或精度丢失 | 阻断加载，人工确认 |
| 删除字段 | 下游报错或变 NULL | 上游变更前应有通知机制（数据契约） |
| 语义变更 | **最危险**：字段名类型都没变，含义变了 | 只能靠上下游沟通 + 数值分布监控发现 |

**防御手段**：
1. **schema 断言**：每次加载校验列名、类型、必填性，不符就阻断并告警
2. **分布监控**：核心字段的空值率、唯一值数、数值分布分位数，与历史对比。
   语义变更通常表现为分布突变
3. **数据契约**：把 schema 与 SLA 写成上下游共同承认的文档/配置，变更需走评审

## 八、数据质量：把断言嵌进管道

用 `scripts/data_quality_check.py` 配合 `assets/data-quality-rules.json`，
在每个分层的产出后运行。检查分两类：

**硬断言（失败即阻断）**：
- 主键唯一
- 必填字段非空
- 行数在合理区间（相比历史同期，不是固定值）
- 关键枚举值都在白名单内
- 与上游的总量对账在容忍误差内

**软断言（告警但不阻断）**：
- 数值分布分位数偏移超过阈值
- 新出现的枚举值
- 缺失率上升
- 环比波动超过历史 P95

阈值一律**基于历史分布动态计算**。固定阈值在业务增长后会失效，在大促时会刷屏。

## 九、成本控制

数据管道的成本容易失控且很难察觉，几个高杠杆动作：

- **分区裁剪**：确保所有查询都带分区条件。一个忘写分区的定时任务可能每天烧掉数千元
- **只选需要的列**：列存下 `SELECT *` 的成本是选 3 列的十几倍
- **物化中间结果**：被 10 个下游重复计算的逻辑，落成中间表
- **生命周期管理**：raw 层冷归档，明细表设 TTL，不是所有数据都要永久在线
- **调度频率复核**：每 5 分钟跑一次但业务只看日报的任务，是纯浪费
- **成本归属打标**：给每个任务打上负责人和业务线标签，账单才能被追责

## 十、可运维性检查清单

一条管道上线前，确认这些都有：

- [ ] 幂等：重跑安全，有明确的重跑命令
- [ ] 依赖：显式声明，不依赖时间巧合
- [ ] 分区：按事件时间分区，支持按分区重算
- [ ] 断言：schema 校验 + 数据质量检查，失败阻断下游
- [ ] 告警：失败告警 + SLA 超时告警，有明确接收人
- [ ] 日志：每次运行记录输入行数、输出行数、耗时、过滤统计
- [ ] 血缘：能回答"这张表由谁产出、被谁消费"
- [ ] 回填：有可执行的回填流程，走同一套代码
- [ ] 文档：字段口径、更新频率、已知限制写在能被找到的地方
- [ ] 负责人：有明确的 owner，不是"数据组"
